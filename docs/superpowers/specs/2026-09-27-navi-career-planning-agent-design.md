## 1. 项目概述

### 1.1 问题背景

大学生生涯规划存在三个结构性问题：

1. **迷茫**——学生不知道有哪些路可走，也不清楚每条路意味着什么。
2. **信息差**——各条生涯路径的真实规则、时间线、隐形门槛分散在学校官网、学长经验、招聘公告中，缺乏系统整理，且质量参差不齐。学生获取到的信息常常过时、片面或错误。
3. **时间窗口的刚性**——大学路径选择具有强时间窗口性：保研看前五学期绩点、夏令营在大三下、秋招在大四上、考公有应届生身份限制。错过窗口的决策成本极高，而学生对窗口的认知往往来得太晚。

### 1.2 产品目标

构建一个生涯规划 Agent，达成以下目标：

- 让学生看清**不同目标对应哪些大学路径**，以及每条路径的完整真相（时间线、硬门槛、软门槛、常见误区、选择它的代价）。
- 基于学生的实际情况给出**个性化路径推荐**，并说明推荐理由。
- 让推荐结果**可解释、可追溯**，学生能理解「为什么推荐这条」以及「我差在哪里」。
- 帮助学生建立**日常任务与长期目标的关联**，明确不同路径下日常侧重点的差异。

### 1.3 设计原则

| 原则 | 含义 |
|---|---|
| **确定性优先** | 路径筛选与打分由确定性算法完成，不依赖大模型推理。模型输出的波动不影响推荐结果。 |
| **可解释** | 每个推荐结果都能分解到具体指标与权重，前端可展示「为什么」。 |
| **可追溯** | 知识库内容标注校对状态，学生能分辨哪些信息已经核实。 |
| **诚实边界** | 对无法可靠回答的问题（如转专业政策细节）明确拒答并给出查询指引，不编造。 |
| **优雅降级** | 大模型不可用时，核心诊断结果仍完整可用；知识库出现未知内容类型时，前端降级为富文本渲染。 |
| **内容与代码解耦** | 知识库以 Markdown/YAML 编写，内容维护者无需接触代码。 |

### 1.4 覆盖范围

**支持的路径（7 条）**

| 目标方向 | 本学科延续 | 跨学科迁移 |
|---|---|---|
| 学术深造（保研） | 本学科保研 | 跨学科保研 |
| 学术深造（考研） | 本学科考研 | 跨学科考研 |
| 市场就业 | 本学科本科就业 | 跨学科本科就业 |
| 体制内 | 考公考编 / 选调生 | — |

体制内路径不按学科跨度切分为两条路线。学科跨度的影响体现在**可选岗位范围**上（专业对口岗与三不限岗的差异），而非路径规则本身的差异，因此由岗位层面的知识描述承载。

**明确不覆盖**

- **出国留学**：资金门槛高，目标受众窄，不作为 MVP 范围。
- **转专业**：不作为推荐路径输出。各校各学院转专业政策年度变动大、院系差异显著（绩点门槛、名额、是否降级转），无法给出可靠建议。学生主动询问时，由诚实边界机制给出拒答与查询指引（见 §8.4）。但「学科认同」指标会保留，学科认同度低的学生，推荐结果会自然偏向跨学科路径。

### 1.5 项目性质与约束

- 比赛作品，由小团队分工开发，需要清晰的模块边界以支持并行工作。
- 开发周期有限，需优先打通端到端最小闭环，再打磨表现层。

## 2. 核心概念模型

### 2.1 两条正交的轴

系统不按「读研 / 就业 / 体制内」的粗分类组织路径，而是使用两条正交的轴：

- **目标方向**：学术深造 / 市场就业 / 体制内
- **学科跨度**：本学科延续 / 跨学科迁移

两条轴交叉出的才是学生真正要走的「路」。本学科保研与跨学科保研是两套不同的规则体系（前者主要竞争绩点排名，后者还需应对先修课缺口、跨考基础、导师意向），本学科就业与跨学科就业同理。

### 2.2 指标（8 项）

所有指标均为 0–100 连续量。指标衡量的是**相对位置或倾向**，而非客观事实——绝对分数（如原始绩点）在不同学校之间不可比。

| 指标 ID | 名称 | 衡量内容 |
|---|---|---|
| `academic-interest` | 学术志趣 | 对深入一门学科、从事研究的真实兴趣（不等同于成绩好） |
| `gpa-competitiveness` | 绩点竞争力 | 在本校本专业中的相对位置 |
| `discipline-identity` | 学科认同 | 对当前专业的认同程度 |
| `cost-tolerance` | 深造成本承受力 | 家庭可支持的教育年限、能否接受延迟就业 |
| `risk-preference` | 风险偏好 | 求稳（一次上岸）与敢赌（广撒网、接受不确定性）之间的倾向 |
| `stress-endurance` | 抗压续航 | 能否承受 1–2 年高强度备考或求职的持续消耗 |
| `public-affairs-leaning` | 公共事务倾向 | 对体制内工作内容的真实适配度 |
| `accumulation-drive` | 积累行动力 | 主动积累经历、技能、产出的行动倾向 |

**关于「学历刚需度」**：该指标曾被考虑，但被排除。原因是它并非学生属性，而是外部事实——「目标职业的学历门槛」属于路径知识的属性。该信息改由知识库承载，供资格过滤规则使用（如「高校教职 → 博士为硬门槛」）。

### 2.3 画像原型

系统定义 6–8 个画像原型。每个原型包含：

- 一个 8 维指标向量（原型中心）
- 一段文案包：一句话人设、优势、盲点、典型困境、建议

学生与每个原型计算相似度，输出**软归属**（如「68% 稳健学术型 + 25% 务实市场型」），而非硬分类。人数本身不适合被硬分到单一类别，软归属更符合实际，也更诚实。

**原型的双重作用**：

| 机制 | 数学 | 决定 |
|---|---|---|
| 路径匹配度 | 各指标与路径理想值的接近程度，按路径权重加权 | 推荐哪几条路 |
| 画像聚类 | 指标向量与原型向量的余弦相似度 | 怎么讲故事 |

两者共用同一个指标向量，但互不依赖，可各自独立测试与调参。

## 3. 系统架构

### 3.1 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | TypeScript | 全栈统一，前后端共享类型定义 |
| 包管理 | pnpm workspace | Monorepo，清晰的工作包边界 |
| 核心逻辑 | 纯 TypeScript，零框架依赖 | 可独立单测 |
| 后端 | Hono | 轻量、TS 友好、内置静态文件托管 |
| 前端 | React + Vite + TailwindCSS | 纯 SPA，无 SSR 心智负担 |
| 图表 | Recharts | 雷达图、条形图开箱即用 |
| 路径地图 | 自绘 SVG + d3-hierarchy | 树形布局 |
| 大模型 | DeepSeek | 国内直连、成本低、API 兼容 OpenAI 格式 |
| 模型接入 | Vercel AI SDK（`ai` + `@ai-sdk/openai`） | 与框架解耦，前端 `useChat` 支持流式 |

**技术选型理由**

**不采用 SSR 框架（如 Next.js）**：本产品是工具型应用（填问卷 → 看结果 → 追问），无 SEO 需求，无首屏服务端渲染需求。SSR 框架的核心价值在此不适用，却会引入 App Router、Server Components、水合错误等持续性心智成本。图表库在 SSR 环境下普遍需要 `'use client'` 或动态导入绕过，会挤占内容打磨的时间。

**不采用 Python 后端**：规则引擎与相似度计算均为简单数学运算，Python 无技术优势。引入第二门语言意味着额外的环境配置、CI 配置，且前后端无法共享类型定义，对小团队是净负担。

**不采用 NestJS**：后端仅是「HTTP 薄层 + 调用 `core` 包」，DI、模块、装饰器体系对此逻辑量属过度设计。

### 3.2 目录结构

```
navi/
├── packages/
│   ├── knowledge/          # 知识库（内容主战场，与代码解耦）
│   │   ├── meta.yaml          # 全局注册表：路径、指标、原型索引
│   │   ├── indicators/        # 8 个指标定义
│   │   ├── archetypes/        # 画像原型定义
│   │   ├── questions/         # 问卷题目与指标映射
│   │   ├── paths/             # 路径文档
│   │   └── boundaries.md      # 诚实边界清单
│   ├── core/               # 纯逻辑层，零框架依赖，可单测
│   │   ├── scoring/           # 指标计算、权重重归一化
│   │   ├── eligibility/       # 资格过滤
│   │   ├── matching/          # 路径匹配度
│   │   └── archetype/         # 画像软归属
│   └── llm/                # 提示词与模型编排
│       ├── prompts/           # 提示词以 .md 存放，不硬编码
│       └── context/           # 追问上下文组装
├── apps/
│   ├── api/                # HTTP 薄层
│   └── web/                # 前端与可视化
└── docs/
```

### 3.3 分层原则

**「逻辑分离」通过包边界实现，而非进程边界。** `core` 是纯函数库，不依赖任何框架、不发起任何网络请求；`llm` 依赖 `core` 的类型；`api` 是编排层；`web` 只消费 HTTP 接口。

**部署形态**：开发期为前后端双进程（各自热更新，互不干扰）；生产期由 `api` 服务托管前端构建产物，形成单服务、单端口、零 CORS 的部署。两套形态共用同一份代码，差异仅在启动脚本与静态文件中间件配置。

### 3.4 HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/questions?grade=&major=` | 获取问卷。服务端按年级/专业返回适配后的题目集（见 §5.4） |
| `POST` | `/api/diagnose` | 提交答案，返回结构化诊断结果（不含模型生成内容） |
| `POST` | `/api/interpret` | 基于诊断结果生成个性化解读（流式） |
| `POST` | `/api/chat` | 追问（流式） |
| `GET` | `/api/knowledge` | 获取路径地图数据 |
| `GET` | `/api/knowledge/:pathId` | 获取单条路径的完整文档 |

`/api/diagnose` 是系统的核心接口，其响应完全由 `core` 层计算，不调用大模型。

## 4. 数据流

```
学生填写问卷（全部题目必答，分组卡片式呈现）
        ↓
[core] ① 指标计算       → 8 维分数
        ↓
[core] ② 作答一致性计算 → 每个指标的可靠性
        ↓
[core] ③ 资格过滤       → 硬约束剔除 / 软约束降权
        ↓                 ← 读取 knowledge：路径前置条件
[core] ④ 匹配度打分     → 每条路径 0–100，排序
        ↓
[core] ⑤ 画像软归属     → 与原型算余弦相似度，softmax 归一
        ↓
════════ 至此为纯确定性计算：无网络请求、无模型调用 ════════
        ↓
[llm]  ⑥ 个性化解读     → 结构化结果 + 选中路径知识 → 解读文本
        ↓
[web]  ⑦ 结果呈现       → 画像卡片 / 雷达图 / 匹配条形图 / 路径地图 / 路径详情
        ↓
[llm]  ⑧ 追问          → 当前路径知识 + 画像摘要 + 对话历史（流式）
```

### 4.1 关键设计决策

**决策一：大模型不在关键路径上。**

步骤 ①–⑤ 为纯函数计算，不依赖网络与模型。当模型 API 超时、失败或欠费时，学生仍可看到完整诊断结果——画像、分数、路径推荐、时间线全部可用，仅缺少个性化解读文字。此为优雅降级，保证演示与使用的稳定性。

**决策二：追问不走向量检索。**

知识库本身具有结构（按路径 × 主题分文件），据此采用**结构化预加载**替代向量检索：

- 单条路径的文档规模为 KB 级，可直接全文载入上下文
- 跨路径问题通过路径标签与关键词做粗筛，选出 2–3 个相关文档
- 不引入向量库、嵌入模型、数据清洗链路

该方案免除了 RAG 全套基础设施，且检索结果完全可控，不会召回无关片段干扰模型。

**决策三：匹配度与聚类是两套独立数学。**

二者共用同一指标向量，但计算互不依赖，可分别单测与调参（详见 §2.3、§7）。

## 5. 问卷设计

### 5.1 出题原则

三种题型原则组合使用：

| 原则 | 做法 | 反面示例 |
|---|---|---|
| **场景式** | 给出具体情境，避免抽象提问 | 「你对学术研究有兴趣吗？」 |
| **侧面式** | 询问行为与反应，避免自我评价。此举可绕过社会赞许性偏差——学生倾向于不承认自己抗压差、不努力 | 「你的抗压能力强吗？」 |
| **程度式** | 五档程度递进，而非并列选项 | A/B/C/D 并列选项 |

### 5.2 五档评分映射

```
①  0 分      ②  25 分      ③  50 分      ④  75 分      ⑤  100 分
否定 ──────────────────────────────────────────────── 肯定
```

题目方向**统一设计为「档位越高 = 该指标越高」**，不引入反向计分，降低实现与维护复杂度。

### 5.3 题目示例

**场景式 + 程度式（测 `academic-interest`）**

> 导师给你一篇 20 页的英文文献，让你一周后汇报。你的第一反应更接近哪一端？
>
> ① 头疼，先找找有没有中文解读
> ② 能读，但大概率拖到最后两天
> ③ 按部就班读完，把汇报做完就行
> ④ 有点期待，会顺便查查相关文献
> ⑤ 很兴奋，希望借这个机会深入这个方向

**侧面式（测 `stress-endurance`）**

> 连续三周高强度备考，第三周某个晚上你发现自己效率明显下降。你更可能：
>
> ① 就此松懈，之后几天都提不起劲
> ② 硬撑，但状态越来越差
> ③ 调整节奏，休息一晚再继续
> ④ 主动换方法，比如换科目、找同学互相抽查
> ⑤ 早有预留缓冲，节奏一直在掌控中

**按年级分流（测 `gpa-competitiveness`）**

大一年级版本：

> 入学后第一次作业或小测，你和身边同学的差距给你的感觉是——
>
> ① 我明显落后，有点慌
> ② 落后一点，需要追
> ③ 差不多，大家都在同一起跑线
> ④ 我稍微领先
> ⑤ 我明显靠前，但还不确定能不能保持

大二及以上版本：

> 你的专业排名大致在——
>
> ① 后半段  ② 中下  ③ 中游  ④ 前 30%  ⑤ 前 10%

### 5.4 年级分流机制

部分指标在低年级缺乏可观测数据（典型为「绩点竞争力」——大一学生尚无排名）。处理方式：

1. **题目分流**：同一指标在不同年级由不同题目测量，保证每道题对目标年级均可作答。低年级使用代理观测（高考位次、入学后首次测验感受）。
2. **权重按年级覆盖**：同一路径权重表中，低年级阶段自动下调依赖该指标的权重。

```yaml
weights:
  gpa-competitiveness:
    default: 0.35            # 大二及以上
    byYear:
      freshman: 0.15         # 大一：信息可靠性低，权重下调
```

### 5.5 答题体验

- **分组卡片式**：4–6 题一屏，每组配引导语（如「先聊聊你和现在专业的关系」），避免一次性呈现全部题目。
- **进度条与组标题**：学生可知剩余进度。
- **全部题目必答**：未完成当前分组不可进入下一组。
- **本地暂存**：答案实时写入 localStorage，中途关闭后可续填。

## 6. 知识库设计

知识库是全系统的核心资产。设计目标：**支持内容自由生长，同时保证前端渲染稳定**。

> **核心机制：自由文档 + 稳定的块级契约 + 优雅降级。**
> 新内容可以在前端支持它之前先写入知识库，内容侧与渲染侧解耦。

### 6.1 目录结构

```
packages/knowledge/
├── meta.yaml              # 全局注册表
├── indicators/            # 指标定义（各一个文件）
├── archetypes/            # 画像原型（各一个文件）
├── questions/             # 问卷题目 → 指标映射
├── boundaries.md          # 诚实边界清单
└── paths/                 # 路径文档
    ├── same-discipline-baoyan/      # 本学科保研
    ├── cross-discipline-baoyan/     # 跨学科保研
    ├── same-discipline-kaoyan/      # 本学科考研
    ├── cross-discipline-kaoyan/     # 跨学科考研
    ├── same-discipline-job/         # 本学科本科就业
    ├── cross-discipline-job/        # 跨学科本科就业
    └── civil-service/               # 体制内（考公考编 / 选调）
```

### 6.2 文件级元数据

每个路径文档的 frontmatter 保持极简且长期稳定：

```yaml
---
id: same-discipline-baoyan
title: 本学科保研
category: academic          # academic | employment | civil
span: same-discipline       # same-discipline | cross-discipline
status: verified            # draft | review | verified
updated: 2026-09
summary: >                  # 200–300 字核心摘要，供追问上下文使用
  保研的实质是……
---
```

**`status` 校对状态是产品信任机制的一部分。** 前端对 `draft` 内容显示「此部分待核实」角标。对一个以「抹平信息差」为承诺的产品，明确标注哪些信息尚未核实，比暗示全部可信更可靠。

### 6.3 块级契约

正文使用 Markdown，语义段落通过 `@block` 注解标记类型：

```markdown
<!-- @block type="timeline" -->
## 保研时间线
```

**三个设计要点：**

1. **块类型开放**：新增内容类型（如 `case`、`compare`）无需修改任何 schema。

### 6.4 编译与渲染

## 7. 核心算法层

`packages/core` 为纯逻辑层：零框架依赖、零网络请求、全部为纯函数，输入输出均为普通对象。

### 7.1 指标计算

题目得分区间为 0–100。单个指标由多道题测量，取加权平均：

```
score(indicator) = Σ(题目得分 × 题目权重) / Σ(题目权重)
```

**约束**：每个指标至少由 3 道题测量。§7.3 的作答一致性以题目得分的离散程度为依据，题目数量过少时该度量不具统计意义。

**未知状态**：全部题目必答，因此正常流程下不产生 `unknown`。`unknown` 作为容错机制保留（应对数据异常、未来新增题目等情况），但不再是主路径。

### 7.2 权重重归一化

每条路径在知识库中定义权重向量，权重和为 1。学生已知指标集合为 `K`，未知集合为 `U`：

```
W'[i] = W[i] / Σ(k ∈ K) W[k]      当 i ∈ K
W'[i] = 0                          当 i ∈ U
```

该机制在正常流程下不触发，作为鲁棒性保障存在。

### 7.3 作答一致性

置信度的来源。同一指标下的多道题应指向同一构念；若学生的回答高度离散，说明其在该维度上的自我认知不一致，据此下调置信度。

```
consistency(i) = max(0, 1 − stdev(指标 i 各题得分) / 50)
```

标准差理论最大值为 50（一半得 0 分、一半得 100 分），此时一致性为 0。

### 7.4 置信度

```
confidence(path) = Σ(W'[i] × consistency(i))
```

其中 `W'` 为 §7.2 重归一化后的权重（和为 1），因此该式为一致性按路径权重的加权平均。

即：权重越高、作答越自洽的维度，对这条路径的判断越可靠。学生若在「学术志趣」上回答前后矛盾，则依赖该维度的路径置信度自动降低。

置信度须在前端展示，并附具体原因：

> **本学科保研 · 匹配度 78** · 置信度 74%
> ⚠️ 你在「学科认同」上的回答前后不太一致，可能你自己也还在犹豫

### 7.5 资格过滤

每条路径声明前置条件，供确定性过滤。缺少此环节会产生荒谬推荐。

```yaml
eligibility:
  - id: has-tuimian-quota
    question: 你的学校是否具备推免资格？
    severity: hard
    failMessage: 你的学校没有推免资格，这条路对你当前不成立
  - id: gpa-threshold
    severity: soft
    failMessage: 你的绩点位置距保研线较远，需要显著投入追赶
```

- `hard` 失败 → 路径标记为「不适用」
- `soft` 失败 → 路径保留，匹配分打折

**设计决策：「不适用」的路径仍然显示，不隐藏。**

隐藏会使学生困惑（「为什么没有保研这个选项？」）。显示并说明原因，解释本身就是有价值的信息——「你的学校没有推免资格」这句话，可能正是该学生最需要知道的事。

### 7.6 匹配度计算

朴素做法是「指标越高越好」，但这是不准确的：指标并非越高越好，而是要看是否匹配。保研需要偏稳的风险偏好，而市场就业可能更需要敢闯。

因此每个指标按**与理想值的接近程度**计算匹配度：

```
match_i = 100 − |score_i − ideal_i|
```

权重定义中包含理想值：

```yaml
weights:
  academic-interest:    { weight: 0.25, ideal: 85 }
  gpa-competitiveness:  { weight: 0.35, ideal: 90 }
  risk-preference:      { weight: 0.10, ideal: 75 }   # 保研倾向求稳
```

加权汇总：

```
match(path) = Σ(match_i × W'[i]) / Σ(W'[i])
```

**附带的可视化价值**：该模型可直接支撑「学生画像 vs 该路径理想画像」的分维度对比，学生可直观看到差距所在（见 §9.3）。

### 7.7 画像软归属

```
similarity(student, archetype) = cosine(student_vector, archetype_vector)
```

仅对**共同已知维度**计算余弦，缺失维度不参与计算但记录覆盖率。经带温度参数的 softmax 归一化为百分比：

```
affinity = softmax(similarity / τ)
```

输出形如：`68% 稳健学术型 + 25% 务实市场型`。

`τ` 控制分布的软硬程度：调大趋近均分，调小趋近硬分类。此为可调参数。

### 7.8 输出契约

`core` 的输出结构专门为「可解释」设计：

```ts
interface DiagnosisResult {
  indicators: Record<IndicatorId, {
    score: number
    known: boolean
    consistency: number
    sources: QuestionId[]
  }>
  paths: Array<{
    id: PathId
    match: number                       // 0–100
    confidence: number                  // 0–1
    eligibility: {
      applicable: boolean
      hardFailures: EligibilityFailure[]
      softWarnings: EligibilityFailure[]
    }
    contributions: Array<{              // 分项贡献，可绘制瀑布图
      indicator: IndicatorId
      match: number
      weight: number
      contribution: number
    }>
  }>
  archetypes: Array<{
    id: ArchetypeId
    affinity: number                    // 0–1
  }>
}
```

**该结构不含任何模型生成内容**——它是确定性的、可复现的、可完整单测的。大模型仅在此基础上做二次加工。

## 8. LLM 层

### 8.1 职责边界

大模型在系统中承担三项职责，不参与任何决策：

1. **个性化解读**——将结构化诊断结果转述为学生可理解的语言
2. **追问回答**——基于知识库内容回答后续问题
3. **诚实拒答**——知识库未覆盖的内容，明确说明无法回答

该边界保证推荐结果不受模型输出的随机性影响：同一学生多次测评，路径推荐与分数完全一致，仅有解读文字存在措辞差异。

### 8.2 解读场景的输入构造

```
[系统提示]   角色设定、语气要求、硬约束
[学生画像]   8 维分数 + 每项的一致性
[诊断结果]   路径匹配度 + 分项贡献 + 资格警告 + 置信度
[画像标签]   软归属结果
[目标路径]   从知识库按 id 取出，全文载入
[输出要求]   固定结构（分段与篇幅约束）
```

单条路径文档为 KB 级，因此**全文载入，不做检索**。此举使模型输出的每句话都能追溯到知识库中的具体内容，构成防幻觉的第一道保障。

### 8.3 防幻觉约束

写入系统提示词的硬约束：

> 「你**只能**使用 `<knowledge>` 标签内的信息。知识库未覆盖的内容，**禁止**基于常识推测或补充。若学生所问不在其中，必须回答：『这部分我们没有可靠信息』，并指出查询途径。」

第二道保障为**内容可追溯**：知识库的 `status` 状态一并传入，模型被要求在解读中标出哪些信息尚待核实。

### 8.4 诚实边界机制

`knowledge/boundaries.md` 将「系统无法回答什么」也纳入知识资产：

```markdown
:::boundary topic="转专业政策"
各校各学院转专业政策每年都可能调整，且涉及绩点门槛、名额、是否降级转
等大量院系差异，我们无法给出可靠建议。
建议：查询你所在学校教务处官网，或直接咨询辅导员与直系学长学姐。
:::

:::boundary topic="院校录取分数线预测"
我们不预测任何学校任何专业的录取分数。请参考官方招生简章与往年数据。
:::
```

**将「不知道」显式化是本产品的核心设计之一。** 对生涯规划领域而言，错误的信息本身就是信息差的一种形式；一个能明确说明「此问题我答不了、请去何处查证」的系统，其可信度高于一个对所有问题都给出流畅回答的系统。

### 8.5 追问的上下文组装

追问时上下文由四部分构成：

| 部分 | 内容 | 规模 |
|---|---|---|
| 学生画像摘要 | 8 维分数 + 画像标签 | 短 |
| **当前路径全文** | 学生正在浏览的路径文档 | 主要上下文 |
| 最近 N 轮对话 | 维持指代关系 | 中 |
| **所有路径的核心摘要** | 每条路径 200–300 字的 `summary` 字段 | 约 2K 字 |

第四项用于回答跨路径对比类问题（如「保研和考研该如何选择」）。载入摘要而非全文，使 token 规模保持可控。

### 8.6 流式输出

DeepSeek 兼容 OpenAI 接口格式。后端使用 Vercel AI SDK 的 `ai` 核心包配合 `@ai-sdk/openai`（`baseURL` 指向 DeepSeek），可运行于任意 Node 服务；前端使用 `useChat` 获得流式对话体验，无需手写 SSE 解析。

### 8.7 降级策略

| 故障情形 | 表现 |
|---|---|
| 模型超时 / 失败 / 欠费 | 结构化诊断结果完整可用，仅提示「个性化解读暂不可用」 |
| 追问请求失败 | 提示重试，不影响已展示内容 |

### 8.8 提示词管理

提示词存放于 `packages/llm/prompts/*.md`，不硬编码在 TypeScript 中。理由：可 diff、可版本管理、可由非开发人员修改。

## 10. 边界情况

| 情况 | 处理方式 |
|---|---|
| **同一指标上作答前后矛盾** | 置信度下降，并给出温和提示（见 §7.4）。不阻断流程。 |
| **低年级学生未经历的场景题** | 通过年级分流保证每道题对目标年级可作答（见 §5.4）。 |
| **所有路径均 hard 不适用** | 输出「当前没有匹配的路径」，逐条解释原因并给出建议。此为有价值的信息，不是错误页面。 |
| **多条路径分数接近**（如 78 与 76） | 同时推荐，并说明「这两条路径对你很接近，差异在于 X」。不假装能分辨细微差距。 |
| **不属于任何画像原型** | 取最接近的一个，并标注「你的画像比较独特」。 |
| **问卷中途退出** | 答案实时写入 localStorage，返回后可续填。 |
| **某条路径内容尚未撰写** | 显示「此路径内容建设中」，不做空白或报错处理。 |
| **知识库存在未识别块类型** | 前端降级为富文本渲染（见 §6.3）。 |
| **模型服务不可用** | 结构化诊断结果完整可用，仅缺少解读文字（见 §8.7）。 |

## 11. 测试策略

### 11.1 `packages/core` 单元测试

使用 Vitest。该包为纯函数、确定性逻辑，是测试收益最高的部分：

- 权重重归一化的数学正确性（含全未知、部分未知边界）
- 匹配度计算边界（理想值全中 / 全偏）
- 作答一致性的退化情况（全同分、极端分散）
- 资格过滤的 hard / soft 分支
- 余弦相似度的退化情况（零向量、维度缺失）

目标为高覆盖率。核心论点是：**推荐逻辑由确定性算法完成，大模型仅负责表达。**

### 11.2 `packages/knowledge` 校验测试

验证全部文档可解析、`id` 唯一、交叉引用完整。校验失败仅警告不阻断，与 §6.4 的降级策略一致。

### 11.3 端到端：黄金案例集

维护 3–5 个典型学生档案及其期望推荐路径，作为回归测试。

该案例集的附加价值：**同时充当内容校对工具**。知识库修改或权重调参后，运行案例集可观察典型学生的推荐结果是否发生异常漂移，防止内容改动引发意外后果。

## 12. 实施顺序与分工

### 12.1 实施顺序

```
1. 知识库骨架 + 编译脚本        ← 内容侧可立即开工，不被代码阻塞
2. core：指标计算 + 权重重归一化
3. core：匹配度 + 画像软归属
4. 最小前端：问卷 + 纯文本结果   ← 先打通端到端闭环，界面刻意从简
5. 接入 LLM 解读与追问
6. 可视化打磨（雷达图 / 路径地图 / 画像对比）
7. 黄金案例集 + 参数调优
```

**第 4 步刻意从简**：先确认「问卷 → 指标 → 路径推荐」链路正确，再投入时间打磨表现层。反向推进（先做界面）是此类项目最常见的时间损耗来源。

### 12.2 分工

知识库与代码解耦，使得内容工作可以完全并行：

| 角色 | 负责内容 | 前置依赖 |
|---|---|---|
| 内容 | `knowledge/` 下全部文档撰写与校对 | 无，可立即开始 |
| 算法 / 后端 | `core`、`llm`、`api` | 指标定义确定后 |
| 前端 | `web` 与可视化组件 | 输出契约（§7.8）确定后 |
| 全员 | 黄金案例审阅、路径知识交叉校对 | 内容初稿完成后 |

内容维护者无需具备编程能力。

## 13. 待验证项

以下设计基于推理，尚未经过验证。需在 MVP 完成后通过实测确认或调整。

### 13.1 跨路径追问的上下文组织方案

§8.5 提出的四项上下文组装策略（画像摘要 + 当前路径全文 + 对话历史 + 所有路径摘要）**尚未验证**。待验证的具体问题：

- 「所有路径摘要」是否足以支撑「保研与考研如何选择」这类跨路径对比问题
- 2K 字摘要的规模是否合适，是否会导致模型忽略其中的细节
- 学生提问超出全部路径范围时，降级路径是否可接受

验证方式：MVP 完成后，构造跨路径提问样本集实测回答质量。若摘要策略不足，需评估是扩充上下文还是引入轻量检索。

### 13.2 作答一致性公式的参数校准

§7.3 定义 `consistency(i) = max(0, 1 − stdev / 50)`，其中分母 50 取自标准差的理论最大值。该取值**尚未经过验证**：

- 实际作答中题目得分的标准差通常远低于理论最大值，可能导致一致性普遍偏高，失去区分度
- 该参数的合理取值依赖真实作答数据，需在积累一定样本量后校准

验证方式：收集实际作答数据，统计各指标题目得分的标准差分布，据此调整分母或改用其他差异性度量。

## 附录 A：术语表

| 术语 | 含义 |
|---|---|
| 路径（Path） | 一条具体的生涯路线，如「跨学科保研」 |
| 指标（Indicator） | 描述学生特征的 0–100 连续量 |
| 画像原型（Archetype） | 预定义的典型学生类型，用于软归属 |
| 匹配度（Match） | 学生对某条路径的适配程度，0–100 |
| 置信度（Confidence） | 该匹配判断的可靠性，0–1，由作答一致性推导 |
| 软归属（Soft Assignment） | 以百分比表示的多原型归属，非单一硬分类 |
| 块类型（Block Type） | 知识库中语义段落的类型标记，决定前端渲染组件 |
| 硬约束 / 软约束 | 资格过滤中直接剔除路径 / 仅降权并警告的条件 |
| 诚实边界（Boundary） | 系统明确声明无法可靠回答的问题域及查询指引 |
